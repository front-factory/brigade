# Feature: Smooth update (branch feat/smooth-update)

Date: 2026-10-23
Last commit: 7461d57
Base branch: develop

## Goal

Make the update between two Brigade versions smooth, non-destructive and effective.

## Steps

- [x] 1. Preview before writing (interactive confirm) and `--dry-run`
- [x] 2. Obsolete files: removed if untouched, kept and reported if edited, empty folders cleaned
- [x] 3. `.claude/settings.json` merged by keys, `.proposed` fallback when not valid JSON
- [x] 4. Three-way merge of other files (base copy of the last kit version in `.claude/brigade-base/`, line-based diff3 in `src/merge.js`)
- [ ] 5. CHANGELOG excerpt between versions: not started, out of this brief

## Decisions and open questions

- Dry run is non-interactive (like `--yes`): no question, no manifest; it lists the plan, the options file status and the `.gitignore`/`.gitattributes` lines it would add (`appendMissingLines(cwd, dryRun)` computes them without writing).
- Merge: objects by key, arrays as union by value (developer's first), scalars stay the developer's. The manifest keeps the kit hash of settings.json, so the next update merges again.
- settings.json merge: with a base, an entry the kit dropped (object key or array item) is removed from the developer's file if it is still deep-equal to the base, so a changed hook command is replaced. Without a base the plain merge stays (step 3 behaviour).
- A settings.json entry the developer deliberately deleted comes back at the next update (the kit adds what is missing). Accepted by the user; documented in the README.

## Notes

- `installFiles` is split into `planFiles` (reads only) and `applyPlan` (writes); `runInit` inserts the preview between them.
- A file the developer edited and the kit did not change since the last install is `kept`: no `.proposed`, recorded hash unchanged. A `.proposed` left by an earlier version is left alone (never deleted silently), it is removed only once the target matches the kit.

## Step 4: three-way merge

- Base store: `.claude/brigade-base/<kit path without its leading .claude/>` holds the rendered kit content as last installed, committed with `.claude/`. Not for write-once files, the options file or the manifest. Written by the apply phase (never in dry run), removed with an obsolete file.
- Plan rule for a regular file, target != wanted, edited and kit changed, base readable: `merge3(base, current, wanted)`. Clean: write the result (`merged`), manifest hash = kit hash, base = wanted. Conflict: dev file untouched, `<file>.proposed` with markers (`conflict`), proposal rewritten only if its content differs. Decision (as Copier/Cruft): a proposal is delivered once, so on `conflict` and `proposed` the kit hash is recorded and `wanted` becomes the base; the next run is `kept` and silent, the `.proposed` stays as the reminder (not rewritten, not recreated if deleted) until the kit changes the file again. The conflict warning shows only on the run that writes it.
- No base (older install, missing or unreadable): whole-file `.proposed` (delivered once, kit hash recorded), `wanted` stored as base (acceptable: if the dev merges the proposal it is the right ancestor, if they keep their file later differences show as conflicts, never silent loss). Edited + kit unchanged stays `kept`; a missing base is restored there, since kit unchanged means `wanted` is the base.
- Merge result equal to the dev's file (e.g. next run after a no-base proposal, kit unchanged): `kept`, hash = kit hash.
- `src/merge.js`: own diff3 (LCS on lines, anchors = base lines kept by both sides), no dependency, no git. CRLF normalized, result in the dev's line endings. Above 16M table cells it returns null and the caller falls back to the whole-file proposal.
- settings.json keeps its key merge (recorded hash unchanged behaviour); the base only adds removal of dropped entries.
- Dogfood: this repo installs the kit as is, so `.claude/brigade-base/` holds the rendered copies (generated by rendering `templates/web`, not hand-written). `test/dogfood.test.js` checks they equal the rendered templates and that no extra file is there; the existing tests are unchanged.
- Decided: the leading `.claude/` of the kit path is dropped (`.claude/brigade-base/rules/brigade.md`), so no nested `.claude` folder exists in the base folder (Claude Code could load it as duplicate skills, agents or rules). `baseRelative` in `src/install.js`; a path without the prefix keeps its full path.
